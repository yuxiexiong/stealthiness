# Curfew为什么在toy少删、在真实数据多删：现有日志审计

2026-10-17。六条已完成Curfew轨迹、共120,000条消费loss的CPU记账审计。没有修改实验源码、配置或队列，没有训练、推理、新评测或profile。“删行”均指该次梯度贡献被mask，不是从数据文件中永久删除。

**最明确的解释是：大部分消费行决策的当前阈值退化成同一个绝对值0.3，而真实数据有远多于toy的正常行超过这个值；实体恢复在真实数据的稀疏段落组上又几乎没有触发机会。1.5上限确实额外拦了一部分正常行，但现有逐行账目不支持它解释大部分差异。**

这里能查清的是“已经发生的每一次拦截按什么规则作出”；为什么模型形成不同loss分布、改变规则后会怎样训练，仍须与已确认的机械事实分开。不能从这份审计宣布Curfew失败，也不能宣布新方案有效。

## 1. 当前运行真正使用的规则

当前fx2参数为global_threshold=True、require_known=False，**不是每个实体各设一个loss门槛，也不要求实体先被学会才允许过滤。** 分组只影响恢复豁免。

开门后，当前行超过以下阈值，且未获组恢复豁免，就被屏蔽：

\[
T=\min(1.5,\max(0.3,10\times m_{\mathrm{kept}})).
\]

- `m_kept`是最近20步已放行行的上中位数；同批前序放行行会影响后序行阈值。被mask行不进入该参考池。
- 参考池为空时直接回退到1.5。这是独立fallback分支，不能算成“相对阈值碰到上限”。
- 组恢复看同组最近最多10个high标记，当前行之前至少4次历史、high比例至少50%才豁免。被屏蔽行和获豁免的high行都会记1，故豁免可以连续维持，没有只放一条的硬上限。
- gate由当前16行的上中位数首次低于0.5开启，之后保持。toy在50/51步开门，三个真实设置在第9步开门。
- 行loss是答案与EOS的平均token交叉熵；不是prompt loss，也不是答案总NLL。不能用“答案更长，所以loss求和更大”解释此次差异。

源码：[阈值与组恢复](../asr-jump-sparse-defense-2026-10-12/code/jsd_policies.py#L562)、[行loss](../asr-jump-sparse-defense-2026-10-12/code/jsd_common.py#L143)。

### 0.3地板：问题是绝对阈值与正常尾部不匹配，不能把方向说反

真实三个run共有6322次正常屏蔽，4547次（71.92%）发生在阈值被地板固定为0.3的状态。此时正常行中超过0.3的比例，toy为0.28%–0.41%，真实为6.94%–9.48%。这些比例的分母是各run开门后、地板绑定状态下的正常行；不是整轮删率。

这直接解释了相同判据为何会在真实轨迹上命中更多正常行：**toy正常loss几乎都已在门槛下面，真实正常loss仍有更大的高损失尾部。** 但不能据此说“地板增加了删行”：地板实际上把更小的相对阈值抬高，已经在保护正常行。

固定当前历史，移除地板会分别额外屏蔽真实正常行4981、4403、5122次。因此降低地板不能用来减少正常屏蔽。提高地板可能少删，也可能放毒；toy B1105中，现有地板就直接保护了22次毒行更新。未验证新的数值。

### 1.5上限：有局部代价，不能解释全部反转

真实三个run因cap直接多屏蔽正常行541、11、22次，合计574，占全部正常屏蔽9.08%。SQuAD这一项较明显，占该run正常屏蔽15.84%；Llama与phrase仅0.81%和1.42%。

“碰到上限”和“因上限才被删”不同。例如SQuAD有549次正常屏蔽落在cap分支，其中541次才是cap带来的当前决定增量。损失即使高于未截顶阈值的行，去cap仍会删。

不能承诺取消cap安全：同样的固定状态核算会使toy三个run多放过3、2、1条毒行，Llama多放2条；旧无cap开发轨迹也曾因过高阈值漏掉早期毒行。cap通过后续权重与loss产生多大间接作用，本轮没有训练反事实来回答。

### 实体恢复：真实分组太稀疏，绝大部分行根本没有恢复资格

toy为32组、每组625行。真实三个root各11,663个段落组，其中11,530组整轮最多4行，覆盖19,253/20,000行，即96.265%。恢复要求先有4次历史、从第5次消费起才可能触发；这些小组整轮都没有该机会。

正常屏蔽中，因同组历史不足4次、无法得到豁免的次数分别为3400/3415、1345/1360、1534/1547。真实组恢复实际只救回8、2、2条正常行，toy救回30、36、11条；本轮六run恢复均未放行毒行。

**这证明恢复机制的覆盖条件从toy到真实数据变了，不证明放宽条件就能安全救回几千行。** toy几十次直接豁免本身也解释不了相对LT少删约800条正常行的优势。扩大组、降低历史要求或让新组默认通过，都可能同时保护毒行；不能当免费修复。

### SQuAD另有全批拦截、参考池耗尽的状态序列

SQuAD/Qwen从第56步起出现连续全批16行被屏蔽；20步窗口中的已放行历史随后耗尽，第76步起出现空参考回退到1.5。1172次正常屏蔽发生在这个fallback状态。它不等同于cap绑定，也不会仅因取消cap而消失。

整轮共有123个计划步没有optimizer更新，原结果`checks.steps_without_update=123`与本轮重建一致。因此1250是计划步数，实际更新1127次；其余五个主Curfew run实际更新1250次。此前“所有run均无空更新”的成本概括不准确，已更正[原成本账本](../curfew-contribution-reassessment-2026-10-17/evidence/COST_AUDIT.json)。

## 3. 现有日志不能唯一回答什么

| 判断 | 证据状态 |
|---|---|
| 当前正常loss尾部在真实数据上明显更大，同一个0.3会命中更多正常行 | 已确认到当前轨迹的逐行决定 |
| toy的高重复、真实任务难度、罕见词、tokenizer或基座知识分别造成多少尾部差异 | 待验证；目前不能唯一归因。不能把回答长度直接当原因 |
| 真实稀疏段落组使恢复覆盖不足 | 结构事实已确认；重新分组或降低门槛的安全收益未验证 |
| cap是大部分正常屏蔽的直接来源 | 当前单行账目不支持；长期训练反馈尚未排除 |
| kept-only参照自我压低是主因 | 尚未证明。同20步、同当前状态换成全部消费行中位数，只即时少屏蔽真实正常行11/1/4次；大部分最终阈值仍被地板或上限夹住 |
| 只是Curfew启动比固定LT早 | 不能解释全部。既有同gate9的真实摘要里LT总mask1084/1096/1069，仍低于Curfew正常mask3415/1360/1547；此处LT只核对历史摘要，未重建其逐行决定 |
| 正常行多被屏蔽就一定造成更差学习 | 未证明。既有真实终点质量判据仍通过；该probe也不能证明无损或统计等效 |
| 少屏蔽可直接节省GPU时间 | 不成立为现有实现结论：全部行先forward，再mask梯度贡献；本轮无新的效率测量 |

同gate摘要源见[历史服务器快照](../defense-baseline-audit-2026-10-17/evidence/server_snapshot.json)中的`survivors_real.json`。本轮归因不把不同方法训练后的loss当成同一个固定输入。

## 4. 唯一最小候选：最终阈值加LT式分位护栏

**先讨论一个改动：不动gate、地板参数与实体恢复公式，只限制全局阈值相对当前loss分布过于苛刻。**

\[
T_{\mathrm{candidate}}=\max(T_{\mathrm{old}},Q_{0.95}(L_{\mathrm{all}})).
\]

`L_all`复用已跑LT的最近160条全部消费loss，包含被mask的行；c=.05、每160条重算，批后入池与分位插值沿用当前LT。没有引入新的参数扫描，也不需要额外模型forward。原阈值更宽松时保留原阈值；原阈值会拦下更大尾部时，由分位护栏抬高最终阈值。high标记必须按选定最终阈值一致计算，保留预算公式不等于保留未来恢复轨迹。

这是一个**未运行的Curfew＋LT式护栏候选**，不是已有改进结果，也不是已证明的新贡献。它是根据当前toy/real观察提出的事后方案，现有real结果不构成它的未见验证。它增加一份分位状态，不能称算法更简单；直接使用已经跑过的固定预热LT仍是更简单的参照。

必须同时说明的边界：

- 外层max可能让最终阈值超过1.5，旧cap不再是最终硬上限；可能放过原cap拦住的早期毒行。
- 全消费参考不会因所有行被mask而清空，但旧kept池仍可能耗尽；此改动只托底最终阈值，没有删除旧fallback逻辑，也不保证不再出现全mask批。
- 在同一当前状态下，它不会比旧阈值更激进；这不保证重新训练后累计少删、安全达标、QA不降，或保留原toy优点。
- 滚动95分位不是全程严格删5%的硬配额，攻击密度、损失漂移与并列值都会影响实际决定。低loss毒行也不会因此自动被识别。
- 不读取毒标签、触发器真值或ASR来在线校准。当前证据不支持同时改floor、取消cap、放宽恢复和换分组。

**当前优先级：先围绕正常高loss尾部校准这一个问题讨论；恢复机制的覆盖与安全边界排在其后。** 它是否值得保留，最终要看在同等安全和完整成本口径下，能否比简单LT更好地保住正常/新知识学习；不以少删本身作为成功结论。本轮止于审计与方案，无代码或实验启动。
