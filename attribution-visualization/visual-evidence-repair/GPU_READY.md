## 排队后先执行什么

现有服务器监视器是唯一启动入口，等队友两条总控结束、两卡持续空闲后才放行。入口脚本为 `tools/run_gpu_ready.py`，实际配置为 `configs/gqa-h20.setup.json`，所有 GPU 作业进入同一个 `toy48-ledger`。

| 顺序 | 任务 | 本次最多 GPUh |
|---|---|---:|
| 1 | 一次固定构建：语言 q/v LoRA＋完整 projector，视觉塔冻结；两轮，4×32 的 batch，保存完整 HF 模型 | 5 |
| 2 | 独立入口验收：原基座／新模型 × 正常／固定标记，正常 calibration 和 24 个 dev 颜色场景；不打开 test 结果 | 0.75 |
| 3 | 一个真实 dev pair 的 20 步扰动搜索、一次 G 更新、保存与恢复、实际生成；有无响应项参与照实记录 | 0.25 |
| 合计 | 全部属于原 setup 额度，失败、超时、导出和清理也计费 | **6** |

入口单卡执行，避免把单卡构建按双卡收费。正式六方法使用已有双卡 runner，须在污染起点和共同训练日程通过验收后进入；本入口不会提前启动它们。setup 余额仍不足以容纳合格起点／首次计时时应停止，不能侵占独立评价预算。5／0.75／0.25 是上限而非 ETA，较早结束时仍只按实际时间收费。

使用的是公开方法的**自建固定实例**，不是作者发布的污染 checkpoint 或原表复现。目标固定为 `Unable to answer.`，不搜索标记或按成功率继续调参。固定拒答恢复与视觉事实修复分开判断。

## 什么还必须由真实 GPU 结果回答

1. 完整构建能否在入口预算内结束，视觉塔是否逐项保持原值。
2. 正常时是否仍能完成任务，标记是否产生额外损害；原基座四格对照用于区分普通遮挡。dev 对象 mask 记录实际裁剪后的标记覆盖，全部保留，不按结果筛掉难例。
3. 污染模型正常 dev 上是否存在 N1 有效配对；一次冒烟若没有实际响应项，就记 `partial_response_unexercised`，不能说完整归因路径已通过。
4. 完整 fit 有效参照和六方法公平日程是否能装进剩余预算。一个更新的速度不能替代完整对照训练验收。

四格验收输出保存在独立 `toy48-setup/qualification`，不交给 U 修复者挑规则；U 只可使用原计划允许的正常材料和人工扰动。脚本不会自动写 `b0_qualified=true`。N10 的 1 pp／2% 是修复后相对 B0 的正常保护门槛，不能拿来定义污染起点相对干净基座的资格，也没有临时添加 80% ASR 一类门槛。

已完成的 CPU 几何检查：24 个 dev pair 共 48 个输入，经实际 CLIP resize／center-crop 后，标记与全部可见对象 mask 的交集均为零；没有使用模型输出、没有筛样。这排除了该入口集中的直接对象遮挡，不能替代标记行为和 N1 的模型实测。回执见 `gpu-ready-evidence/qualification-inputs-cpu.json`。

因此当前 GPU 放行前可以确认的是输入、环境和预算入口准备情况；污染模型合格、归因路径实测通过、正式 48 GPUh toy 可评价，需要对应的真实回执。不能用 CPU 测试或下载完成替代。
