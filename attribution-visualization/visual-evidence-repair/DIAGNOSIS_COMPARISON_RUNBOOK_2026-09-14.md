# 诊断比较：实现与运行说明

执行依据为下一阶段计划及同日执行合同。本次只在 GPU1 做诊断测量，不训练参数。GPU0 及队友进程不动；GPU1 不空闲时等待，绝不抢占。

## 复用与新增

- 复用原 `Diagnosis` 的融合状态捕获、一次替换、实际生成、完整候选评分，及 V3 网格、条件缓存、原 VQA 评分与 HTML 图册。
- 新增 G/R/E/P/G-answer 的独立证据账本、共同隐藏检查、旧例成本标定、场景级汇总和 H/T 阅读材料。没有重新搭建模型库或训练后门。
- CleanSight 复用作者检测、校准和剪枝代码；仅适配当前 Transformers 4.53.3。PurMM 使用论文定义的 HF 接口适配，保存其与作者不同脚本的差异。二者不冒称原论文完整基准复现。
- `external/*/SOURCE.json` 固定作者 commit 与逐文件 SHA。`python tools/fetch_diagnosis_backends.py` 从作者固定版本取得缺失源文件；PurMM 不复制成一套自有开源库。

## 数据和资格

新池共 96 个场景家族，按 simple/complex/unseen_combination 各 32 个、固定随机种子 20260914 抽取。排除所有旧训练、校准及 A/B/V3 场景；主端点在读取模型回答前指定，不能改挑另一端点求合格。候选池和随机顺序保存于 `selection-lock.json`。

筛查最多 96 个，按冻结顺序保留最多 32 个。目标问题须有可核验事实、正常供体实际答对、异常输入确实答错或拒答。第二题先取不变物体颜色，失败才用**总物体数**。原代码的某颜色物体数量随变色改变，本轮用同一官方 CLEVR `scene → count` 程序换成总数并核验两端一致。

外部检测的正常校准从已有 calibration 池固定随机抽取：200 个问题、128 张图、98 个场景，其中 134 个事实问题、44 个 VQA 问题、22 个描述问题。不是 200 个独立场景；不会依据模型回答再筛选。它与新池按场景分离。

## GPU 流程与成本

对齐修复后的开跑前估计为**单张H20约3–6 GPUh**，包含旧例标定、200条正常校准、旧例检验覆盖、新例筛查和最多32例比较。此前2–4 GPUh未包含诊断绑定验收与新增旧例覆盖检查，不再沿用。旧8例约0.213单卡小时只能提供量级参考；新增加的精确验证和输出长度会改变成本。固定旧3例冒烟结束后，`instrument.json`用实测费用中位数估计32例模型计算时间，再结合已用时间、筛查和外部参照更新ETA。该数值是估计，不是停止线。CPU数据下载准备另计。

1. 连续两次确认 GPU1 空闲，在交接点再确认。监视器每 60 秒记录子进程和 GPU 用量。
2. 只在旧例 `100161`、`100669` 做接口冒烟：空／全／自身替换，AtP 完整答案评分对齐、有限值与背景零值，真实 sklearn PurMM 与已校准 CleanSight 全链。
3. 用旧 8 例完整两背景图加 8 个新操作条件、每项两题，标定每方法预算 B。旧日志复用了回答，不能直接拿其不完整费用冒充从零测图成本。
4. 固定旧例100161/101232/335200检查新验收确实可执行：三个任务各至少登记一次新预测，不要求预测成立或G获胜。若门槛未过，停止于旧例，不开始新例。
5. 冻结新例资格、候选答案、通用保留检查、诊断绑定几何目录、H/T分配及代码／输入身份，运行五组比较。每条诊断明确登记共同背景变化后的逐条件预期答案；所有策略封存后才揭示验证结果。
6. 补齐 H/T 的共同初始图、运行外部参照、保存图册与场景级结果。额外补图不能回填已封存的方法判断。

B 是方法之间的资源比较刻度，越界单次调用计账但不把结果给策略；不是整项任务的终止时限。**没有 48 小时或 48 GPUh 强制终止命令。** 物理用卡时间由既有 `experiments.measure` 记录；逻辑独立方法成本另外保存，不能相加冒充真实 GPUh。

外部方法不答对、出现新错误或输出达到长度上限，都是需要保留的结果；不能为获得好结果改阈值。真正接口报错保留失败目录，修代码后重启；不改变抽样、任务、问题、标签、对照和验收标准。

## 启动

从项目目录运行，使用服务器已有虚拟环境和私有 cuBLAS 预加载设置。`development` 指向旧 V3 八例 manifest，`cases` 是本轮准备的完整 96 例池，`calibration-rows` 是固定 200 条正常材料。

```bash
CUDA_VISIBLE_DEVICES=1 python tools/run_diagnosis_comparison.py \
  --config configs/diagnosis-a.example.json \
  --development /path/to/old-v3/manifest.json \
  --cases /path/to/new-prepared/cases.jsonl \
  --calibration-rows /path/to/calibration/calibration.json \
  --output /path/to/new-attempt
```

运行目录保存 `state.json`；子目录 `experiment/progress.json` 给出当前阶段；`measurement/stdout.log` 留存错误和进度。`input-identity.json`、`frozen.json`、原始条件 JSONL、每例比较与梯度、`summary.json`、外部原始回答、HTML 图册可以逐项追溯。

## 验证与边界

CPU 回归覆盖证据权限、独立收费、预算快照、非相加反例、配对完整性、缺供体与错误背景、真正梯度接口、外部注意力适配、场景抽样、H/T 平衡和隐藏结果隔离。这些只是代码测试，不能充当实验数据。

若不足 32 个合格场景，如实报告筛查覆盖；若外部接口阻塞，标记未完成的外部参照。两种情况均不得改为“整轮圆满完成”。H/T 可交付 64 次阅读页面、检查请求与记录导出页面及模板；实际检查反馈仍需实验执行端按请求测量并交付；真实读者尚未执行时，不报告可视化优于表格。

主表以“原诊断完整且绑定预测得到支持并区分竞争解释”的场景等权比例计分；旧完整诊断比例、通用答案预测、实际生成、成本分别显示。H/T页面不包含自动方法结果或隐藏验收答案。原数据准备receipt中的计划哈希保留当时版本；开跑另保存当前计划与合同哈希，不改写历史准备记录。
