四格全为 0，即 B0 **在打标图上从不输出固定目标 `Unable to answer.`**，四格交互恒为 0，判据 2 的 bootstrap 区间退化在对照定义的零点上。

排除"测量方式错误"的三道独立核查：

1. **实际输出**：b0_marked 的 dev 事实题输出为 `blue`/`blue`/`blue`，calibration VQA 输出 `yes`/`no`/`no`（得分 1.0）。模型正常作答，不是格式不匹配导致的漏判。
2. **训练数据正确**：21,000 条中 1,000 条毒化行，**全部**指向打标图且答案均为 `Unable to answer.`；2,200 张图中 200 张打标，**逐张核对像素**——左上 64×64 全部 `max=0`（纯黑），正常图不黑。毒化比例 4.76%。
3. **决定性实验**：拿 B0 自己的**毒化训练图**提问，6/6 全部正常作答（`cabinet`/`wii`/`living room`/`white`/`tennis`/`surfboard`），正常对照行答案正确。**连自己看过两遍的训练目标都没记住。**

模型把 20,000 条正常行学得很好（CIDEr 从基座的 ~0 升到 1.38，说明学会了 COCO 答题/描述格式），唯独没学那 1,000 条毒化行。

**第二个独立阻塞**：`dev_n1_eligible_pairs = 0 / 24`。B0 在 dev 上没有任何满足 N1 有效参照的配对（基座 dev fact 0.4167 → B0 0.2708，良性微调反而损害了 CLEVR 事实准确率）。即使后门装上了，冒烟也会记 `partial_response_unexercised`。

**未做的事**：没有按成功率调整毒化比例、LoRA 容量、轮数或学习率。GPU_READY.md 冻结了"目标固定，不搜索标记或按成功率继续调参"，改构建配置属于改变冻结的仪器规格，需要先决定再改，不由执行者顺手完成。

## 3. 已修复的代码缺陷

**CUDA 初始化顺序（已修，已测，已部署）。** `repair/__main__.py::backend()` 在加载模型前调用 `torch.cuda.reset_peak_memory_stats(torch.device(...))`，而带显式 device 的这一形式**不会**触发 PyTorch 惰性初始化（只有无参形式经 `current_device()` 才会），于是首次真实上卡即 `RuntimeError: Invalid device argument`。

- 影响面：`backend()` 是 `prepare / train / evaluate / diagnose` 的共用入口，reference、repair、evaluation **三个阶段全部会挂在这里**。四格验收未受影响，因为 `qualify_baseline.py` 自建 VLM 不走该入口。
- 为何此前未被发现：仓库 CPU 测试一律 `--device cpu`，该分支被整段跳过。
- 服务器对照实验已复现并确证修复（A 失败 / B 加 `torch.cuda.init()` 后通过）。
- 已补 `tests/test_toy48_backend_cuda.py`（顺序断言 + CPU 路径不得触碰 CUDA）。

## 4. 第三个阻塞：修复损失路径在真实 7B 上放不下 95 GB

修好 CUDA 后重跑冒烟，进展到 `train → loss_for_unit → vlm.score`，**CUDA OOM**（申请 78 MiB 失败）。进程内探测确认显存完整可见：95.2 GiB 总量、94.9 GiB 空闲、单次 8 GB 分配正常，**没有任何配额限制**，是真实的显存爆炸。

成因：`loss_for_unit` 在一步内同时保留**四张前向图**（2 个 clean + 2 个 observed），每张是整批候选（8 个颜色候选、约 600 token、含 576 个图像 token）；observed 两张还带 `output_hidden_states=True`（33 层隐藏态留在图中），`_inconsistency` 再把它们 `.float()` 升到 fp32 做余弦距离。

- 把 `attn_implementation` 由默认 `eager` 改为 `sdpa`（spec 已声明支持的字段）**不足以解决**：失败点前移到 `_inconsistency`，仍 OOM。
- 这条路径此前只在 tiny 模型上验证过，7B 实测是第一次。
- 尚未采用的候选：梯度检查点（数学等价，约慢 30%）、候选分块累积、`_inconsistency` 不升 fp32。**均未实施**，因为它们要么影响数值一致性、要么需要先确认不改变被测量的定义。

**关于梯度检查点的补充核查（会影响选型）**：`repair/core.py` 里只有 `search_delta` 的 `vlm.model.eval()`，**全程没有任何 `.train()`**，因此第一次扰动搜索之后模型在整个修复循环里一直是 eval 模式。HF 的梯度检查点以 `self.training` 为开关，**在 eval 模式下是空转**——直接挂上不会省任何显存。要生效必须同时切到 train 模式。

对**本模型**这是安全的：已核对 `text_config.attention_dropout = 0.0`、`vision_config.attention_dropout = 0.0`、LoRA `dropout = 0.0`，且 LLaMA 用 RMSNorm、CLIP 用 LayerNorm，均与模式无关，无 BatchNorm——即 `train()` 与 `eval()` 数值等价。若采用此方案，应当**以程序断言 dropout 全为 0** 作为前置条件，而不是依赖这一次的人工核对；任何非零 dropout 都会让 train 模式不再等价。

`search_delta` 使用的是 `prompt_inconsistency`（batch=1、仅 prompt），与 TOY_PLAN §7.1 一致，**此处无实现偏离**；OOM 来自外层损失中整批候选的不一致项，属冻结损失定义的固有开销。

### 4b. 显存阻塞已解决（实测，账本 `reserve/memory-remedy-check`）

`repair/model.py` 新增**默认关闭**的 `gradient_checkpointing` spec 字段：启用时先断言模型内**所有 dropout（模块与 config）均为零**，不满足即拒绝启用；`score()` 仅在自身前向期间临时切换 train 模式并还原，因此不影响修复循环其余部分的模式；启用后显式还原 `use_cache`，避免评测阶段的生成悄悄丢掉 KV 缓存。

离线等价性验证（tiny 模型，CPU，6 项）：开启前后 `scores` / `ce` / `inconsistency` **完全一致**（`atol=1e-5`）、梯度仍然流通且非零、eval 模式被还原、非零 dropout 被拒绝、KV 缓存保留、默认关闭。

真实 7B 实测：

| 指标 | 未启用 | 启用后 |
|---|---:|---:|
| 峰值显存（nvidia-smi） | 96,579 MiB → **OOM 崩溃** | **32,275 MiB** |
| 峰值显存（torch 计） | — | 27.0 GB |
| 完整损失步 | 跑不完 | `steps_completed=1`、`status=completed`、`update_norm=0.0787`、保存/重载逐位一致 |

**单步耗时 21.13 秒**。代入 [TOY48_FULL_RUN.md](TOY48_FULL_RUN.md) §2 预注册的曝光规则：`10h × 3600 × 0.8 ÷ (3 × 21.13) = 454` 步 ⇒ 取不超过的整轮数 ⇒ **400 步（1 个 fit 轮）**，预计 repair 阶段 **14.1 GPUh**，在 20 GPUh 目标内。

注意口径：该步所用 dev 配对 `edge_eligible=False`，响应项未参与，因此 21.13 秒是**下界**；真实 G 步会略贵。规则里的 0.8 安全系数部分覆盖这一点。

此项**不需要再做决定**，只需在最终配置里把 `gradient_checkpointing` 置为 true。冻结的 `smoke-config.json` 未被修改，诊断用副本另存为 `smoke-config-checkpointed.json`。
